# Upgrading from `@kontent-ai/model-generator@10`

Version `10` of `@kontent-ai/model-generator` generated models for every supported SDK. Starting with version `11`, SDK specific models are generated by dedicated packages:

- [`@kontent-ai/delivery-sdk-model-generator`](./packages/delivery-sdk-model-generator)
- [`@kontent-ai/migration-toolkit-model-generator`](./packages/migration-toolkit-model-generator)
- [`@kontent-ai/sync-sdk-model-generator`](./packages/sync-sdk-model-generator)
- [`@kontent-ai/model-generator`](./packages/model-generator) (SDK independent `environment` and `items` models)

## Why the generator was split

A single package targeting the Delivery SDK, Migration Toolkit and Sync SDK at once could not version along with any of them. A breaking release of one SDK forced a major release of the whole generator, and its version number said nothing about which SDK versions it supported.

Each SDK specific generator now shares the major version of the SDK it targets:

| Generator                                         | Targets                           |
| ------------------------------------------------- | --------------------------------- |
| `@kontent-ai/delivery-sdk-model-generator@17`     | `@kontent-ai/delivery-sdk@17`     |
| `@kontent-ai/migration-toolkit-model-generator@3` | `@kontent-ai/migration-toolkit@3` |
| `@kontent-ai/sync-sdk-model-generator@1`          | `@kontent-ai/sync-sdk@1`          |

To pick a generator version, use the major version of the SDK in your project. Each generator is released independently, so an SDK upgrade affects only the generator for that SDK.

## Package and command mapping

| Previously (`@kontent-ai/model-generator@10`) | Now                                             | CLI                          | Programmatic API                 |
| --------------------------------------------- | ----------------------------------------------- | ---------------------------- | -------------------------------- |
| `kontent-generate delivery-sdk`               | `@kontent-ai/delivery-sdk-model-generator`      | `kontent-generate-delivery`  | `generateDeliveryModelsAsync`    |
| `kontent-generate migration-toolkit`          | `@kontent-ai/migration-toolkit-model-generator` | `kontent-generate-migration` | `generateMigrationModelsAsync`   |
| `kontent-generate sync-sdk`                   | `@kontent-ai/sync-sdk-model-generator`          | `kontent-generate-sync`      | `generateSyncModelsAsync`        |
| `kontent-generate environment`                | `@kontent-ai/model-generator@11` (unchanged)    | `kontent-generate`           | `generateEnvironmentModelsAsync` |
| `kontent-generate items`                      | `@kontent-ai/model-generator@11` (unchanged)    | `kontent-generate`           | `generateItemsAsync`             |

## Migration steps

1. Install the generator for your SDK, for example:

   ```bash
   npm i @kontent-ai/delivery-sdk-model-generator@latest --save-dev
   ```

2. Update CLI calls. The SDK specific packages have no subcommand, and all options stay the same:

   ```bash
   # Before
   npx @kontent-ai/model-generator@10 delivery-sdk --environmentId=<id> --managementApiKey=<key>

   # After
   npx @kontent-ai/delivery-sdk-model-generator@latest --environmentId=<id> --managementApiKey=<key>
   ```

3. Update programmatic calls. Only the import path changes, the configuration object stays the same:

   ```typescript
   // Before
   import { generateDeliveryModelsAsync } from "@kontent-ai/model-generator";

   // After
   import { generateDeliveryModelsAsync } from "@kontent-ai/delivery-sdk-model-generator";
   ```

4. Regenerate your models and update your code for the changes listed below.
5. If you only used `delivery-sdk`, `migration-toolkit` or `sync-sdk`, uninstall `@kontent-ai/model-generator`.

## Changes in generated models

### Renamed `Core*` types

The `Core` prefix sounded like a type exported by the SDK. Generated types now use the `Typed` prefix:

| Generator         | Before                    | After                      |
| ----------------- | ------------------------- | -------------------------- |
| Delivery SDK      | `CoreType`                | `TypedItem`                |
| Delivery SDK      | `CoreClientTypes`         | `TypedClientSchema`        |
| Delivery SDK      | `CoreDeliveryClient`      | `TypedDeliveryClient`      |
| Sync SDK          | `CoreSyncClientTypes`     | `TypedSyncClientTypes`     |
| Sync SDK          | `CoreSyncClient`          | `TypedSyncClient`          |
| Migration Toolkit | `CoreMigrationItem`       | `TypedMigrationItem`       |
| Migration Toolkit | `CoreMigrationItemSystem` | `TypedMigrationItemSystem` |

If you used a preview of `@kontent-ai/delivery-sdk-model-generator@17`, `CoreItem` and `CoreClientSchema` are now `TypedItem` and `TypedClientSchema`.

### Migration Toolkit, Sync SDK, environment and items models

Apart from the renamed `Core*` types and the generated file header, the output is unchanged.

### Delivery SDK models

`@kontent-ai/delivery-sdk-model-generator@17` targets `@kontent-ai/delivery-sdk@17`. Models generated by `@kontent-ai/model-generator@10` target `@kontent-ai/delivery-sdk@16`, and models from one version do not compile against the other SDK. For changes in the SDK itself, see the [Delivery SDK migration guide](https://github.com/kontent-ai/delivery-sdk-js/blob/master/migration.md).

The examples below use a content type with codename `movie`.

#### Client and schema

`CoreClientTypes` built from separate codename types is replaced by `TypedClientSchema`, which describes the environment for `DeliveryClient`:

```typescript
// Before
export type CoreClientTypes = {
	readonly collectionCodenames: CollectionCodenames;
	readonly contentItemType: CoreType;
	// ...
};
export type CoreDeliveryClient = IDeliveryClient<CoreClientTypes>;

// After
export type TypedClientSchema = DeliveryClientSchema<{
	readonly languageCodenames: readonly ["en", "cz", "German"];
	readonly contentTypes: {
		readonly movie: readonly ["title", "plot", "released" /* ... */];
	};
	// ...
}>;
export type TypedDeliveryClient = DeliveryClient<TypedClientSchema>;
```

#### Content types

Content type models are built with `ContentItemOf` and end with `Item` instead of `Type`. Names derived from the content type no longer contain `Type`:

| Before                                   | After                                |
| ---------------------------------------- | ------------------------------------ |
| `MovieType`                              | `MovieItem`                          |
| `MovieTypeCodename`                      | `MovieCodename`                      |
| `isMovieTypeCodename`                    | `isMovieCodename`                    |
| `isMovieType`                            | `isMovieItem`                        |
| `MovieTypeElementCodenames`              | `MovieElementCodenames`              |
| `MovieTypeCategoryMultipleChoiceOptions` | `MovieCategoryMultipleChoiceOptions` |
| `CodenameTypeMapping`                    | `TypeCodenameToItemMap`              |
| `CodenameTypeMapper`                     | `TypeCodenameMapper`                 |

```typescript
// Before
export type MovieType = IContentItem<
	{
		readonly title: Elements.TextElement;
		readonly stars: Elements.LinkedItemsElement<ActorType | MovieType>;
	},
	MovieTypeCodename,
	LanguageCodenames,
	CollectionCodenames,
	WorkflowCodenames,
	WorkflowStepCodenames
>;

// After
export type MovieItem = ContentItemOf<
	TypedClientSchema,
	MovieCodename,
	{
		readonly title: Elements.Text;
		readonly stars: Elements.LinkedItems<ActorItem | MovieItem>;
	}
>;
```

File names are unchanged (for example `types/movie-type.generated.ts`).

#### Elements

Element types use the Delivery SDK 17 names, for example:

| Before                                      | After                          |
| ------------------------------------------- | ------------------------------ |
| `Elements.TextElement`                      | `Elements.Text`                |
| `Elements.RichTextElement<CoreType>`        | `Elements.RichText<TypedItem>` |
| `Elements.LinkedItemsElement<T>`            | `Elements.LinkedItems<T>`      |
| `Elements.AssetsElement`                    | `Elements.Asset`               |
| `Elements.DateTimeElement`                  | `Elements.DateTime`            |
| `Elements.NumberElement`                    | `Elements.Number`              |
| `Elements.MultipleChoiceElement<T>`         | `Elements.MultipleChoice<T>`   |
| `Elements.UrlSlugElement`                   | `Elements.UrlSlug`             |
| `Elements.TaxonomyElement<Terms, Codename>` | `Elements.Taxonomy<Terms>`     |

#### Snippets

Snippets are built with `SnippetOf` and list the content types that use them. The snippet codename type and its type guard (`SnippetASnippetCodename`, `isSnippetASnippetCodename`) are no longer generated. Instead, `isSnippetASnippet` checks whether an item is of a content type that uses the snippet:

```typescript
// Before
export type SnippetASnippet = Snippet<
	SnippetASnippetElementCodenames,
	{
		readonly snippet_a__text: Elements.TextElement;
	}
>;

// After
export type SnippetASnippet = SnippetOf<
	TypedClientSchema,
	ContentTypeWithAllElementsCodename | ContentTypeWithSnippetOnlyCodename,
	{
		readonly snippet_a__text: Elements.Text;
	}
>;
```

Content types that use a snippet now combine their elements with the snippet's elements (`{ ... } & SnippetASnippet["elements"]`). Previously they were combined with the whole snippet type (`{ ... } & SnippetASnippet`).
